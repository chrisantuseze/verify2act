## History of Failed Training Runs

Five training runs across different architectures all produced AUROC ≈ 0.51 on validation. Summary:

| Run | Architecture | Loss used | Result |
|---|---|---|---|
| 1 | VAE latent + Transformer | BetaNLLLoss | AUROC ≈ 0.50, loss = −1.46 (arcsine collapse) |
| 2 | VAE latent + Compare MLP | PRMCriticLoss (BCE) | AUROC ≈ 0.50, loss flat at 0.693 = log(2) |
| 3 | VAE raw latent + strided conv | PRMCriticLoss | AUROC ≈ 0.50, loss 0.687→0.684 |
| 4 | ResNet-18, single LR=1e-3 | PRMCriticLoss | AUROC noisy 0.47–0.53, loss 0.708→0.683 |
| 5 | ResNet-18, two-phase + differential LR | PRMCriticLoss | Train loss → 0.03, val AUROC ≈ 0.51, val loss → 2.0+ (memorization) |

### Root cause (proven, not hypothesised)
Binary `label_reachable` from `compute_labels.py` is generated by restoring full simulator state (qpos/qvel from `.npz`) and running an expert policy for H steps to check task success. **This label is a function of hidden sim state — not of the RGB image.** A camera cannot see joint angles, contact forces, or gripper state.

Diagnostic proof: computed AUROC of −L2(z_t1 − z_goal) as a zero-training predictor:
- L2: AUROC = 0.5103
- L1: AUROC = 0.4966
- Cosine: AUROC = 0.5106
- L2 pos mean = 97.1992, neg mean = 97.7980 (0.6% difference — pure noise)

**Conclusion: no architecture or loss can learn this signal from RGB, because the signal is not in RGB.**

Additionally diagnosed:
- **Run 1 failure**: BetaNLLLoss pathology — model learns α≈β≈0.5 (arcsine distribution), loss ≈ −1.46. Fixed by switching to PRMCriticLoss (BCE on α/(α+β)).
- **Run 4 failure**: lr=1e-3 too high for pretrained ResNet-18 backbone — ImageNet features destroyed in epoch 1. Fixed by two-phase training (freeze backbone for N epochs, then unfreeze with backbone_lr=1e-5).
- **Run 5 failure**: Memorization — model fits training set (7825 samples) perfectly but generalises to nothing. Classic symptom of the supervision signal being spurious pixel correlations rather than real structure.

This prevents the model from cheating by memorising episode-specific visual patterns. The new `ContrastivePairDataset` must maintain the same split strategy — sample pairs only from within-split episodes.

**Goal image validity concern** (discussed explicitly): the goal image `I_goal` is the fully solved scene (all nuts on pegs). This was raised as potentially wrong signal for intermediate states — a state where one nut is placed correctly but another is still on the table has no visual reference in `I_goal`. This concern is resolved in the contrastive design by restricting critic evaluation to the **final imagined frame only** (step H), where the world model has had H steps to get close to the goal. At the final step, `I_goal` is the right reference. For intermediate steps, the hard sanity filter approach (not goal-image comparison) is used instead.

## Three Paths Considered

### Path A: VLM-as-Verifier (zero training)
Use a pretrained VLM directly as the critic. Send `(I_current, I_imagined_final, I_goal, task_description)` to a VLM; get back a progress score and explanation.

**Why rejected**: This collapses Verify2Act into ReflectVLM. ReflectVLM (Feng et al., 2025, Cornell/Berkeley) already does exactly this — VLM proposes action, diffusion model imagines future, **same VLM reflects and revises** based on `(I_current, I_imagined, I_goal)`. The four-module Verify2Act pipeline becomes structurally identical. The entire architectural contribution (decoupled specialized critic) is lost.

### Path B: State oracle baseline (diagnostic only)
Train a simple MLP on raw simulator state (qpos/qvel from `.npz` files) → binary label. If this gets AUROC >> 0.5, the labels are meaningful but just not visually observable. If even this fails, the label generation itself (compute_labels.py horizon, expert policy quality) needs fixing.

**Status**: Not yet run. Still recommended as a 30-minute sanity check before building the new critic.

### Path C (chosen): Contrastive goal-proximity critic on demonstration temporal ordering
See full design below.

Proposed but rejected: use `skill_name`/`stage` from `transitions_subskill.jsonl` as classification target instead of binary reachability. The stages are `approach → carry → align → insert` for NutAssembly.

- The stages are also heuristic boundaries within a continuous motion — they don't correspond to discrete physically meaningful events.

## Discussion: Contribution Framing vs ReflectVLM

Verify2Act's architectural contribution is the **decoupled specialized critic**:

| | ReflectVLM | Verify2Act |
|---|---|---|
| Verifier | Same 7B VLM, self-reflection prompt | Separate specialized model, contrastive fine-tuned |
| Verification target | Semantic reasoning ("does this make sense?") | Learned visual proximity to demonstration outcomes |
| Speed | ~2–5s per query (full VLM forward pass) | ~20ms (ViT encoder only) |
| Physical grounding | Internet priors (VLMs frequently wrong about physics) | Learned from actual domain dynamics |
| Labels needed | None | Trajectory success/failure (already collected) |

The moat: VLMs reason semantically from internet text. Your critic learns the **physical manifold** of what progress looks like in your specific domain — 7000+ rollouts of actual manipulation dynamics. VLMs are consistently wrong about physics precisely because they've never experienced physics; they've only read about it.

This distinction holds as long as the critic is a *separate trained module*, not another VLM call.

### Contribution strength analysis (from follow-up review)
Speed (20ms vs 2–5s) alone is an engineering result. "Physically grounded" is a claim that needs empirical demonstration. Three angles to strengthen the contribution:

1. **Temporal consistency for intermediate frames** (see dedicated section below) — evaluating rollout integrity from RGB without 3D predicates is genuinely open and not addressed by ReflectVLM or P2P. This is the highest-leverage addition.

LLM self-critique is a known failure mode (Huang et al., 2023, "Large Language Models Cannot Self-Correct Reasoning Yet"). 3. **Critic fine-tuning under world model distribution shift** — Including diffusion-generated images in fine-tuning is domain adaptation. Confirm with an ablation showing it matters.

## Agreed Design: Contrastive Goal-Proximity Critic

### Core idea
Train a **DINOv2-B/16** vision encoder contrastively on demonstration trajectories. The critic score at inference is:

```
critic_score = cosine_sim(encode(I_imagined_final), encode(I_goal))
```

No binary labels. No sim-state restoration. Labels come entirely from the temporal structure of expert rollouts.

### Why the target changes from binary reachability to goal proximity
The question "will an expert succeed within H steps from this state?" requires knowing hidden sim state, so it is not learnable from RGB. The question "does this imagined final frame look like the goal, based on what I've seen in successful demonstrations?" IS answerable from RGB — early trajectory frames look nothing like the goal; late frames in successful episodes look almost identical to it.

This is the key insight: use the **temporal ordering** of demonstrations as a free supervision signal, instead of trying to predict a quantity that isn't in the image.

### Why per-step evaluation is harder than final-only
User raised: should we also evaluate intermediate imagined frames? The answer is that per-step soft progress is harder because there is no fixed visual reference for what "40% done" looks like — it varies with the trajectory. The final imagined frame H has a reference: `I_goal`. That's why the proposal evaluates the final frame contrastively and handles intermediate frames differently (see Points2Plans section below).

### Training data construction (no new data collection needed)
From existing expert trajectory images:
- **Positive pairs**: `(I_late_frame, I_goal)` — frames from the last 20% of timesteps in a successful rollout, paired with that episode's goal image. These look like the goal.
- **Negative pairs**: `(I_early_frame, I_goal)` — frames from the first 20% of any trajectory, OR any frame from a failed trajectory. These don't look like the goal.
- **Loss**: InfoNCE (contrastive)

Labels come free from: (1) the success flag in episode metadata, (2) the timestep position within the trajectory. Zero sim-state restoration. Zero new annotation. Zero `compute_labels.py`.

### Why this generalizes (unlike stage classification)
The learning principle — temporal ordering of demonstrations indicates goal proximity — is domain-agnostic. You can apply it to pick-place, stacking, or sorting by fine-tuning on demonstrations for that task. The critic architecture doesn't change; only the training data does. This is a genuine generalization claim.

Related work that uses the same principle: GCSL (Ghosh et al.), contrastive RL (Eysenbach et al.), QuaSAR. These all derive supervision from trajectory structure without explicit reward labels.

## Encoder Choice: Why DINOv2-B/16 over SigLIP

### Initial recommendation: SigLIP-B/16
SigLIP was initially recommended because it uses sigmoid loss on image-text pairs (better calibrated than CLIP's softmax over batches), and is a strong visual-semantic encoder. It is better than CLIP for image-image matching tasks.

### Why DINOv2-B/16 is better for this specific task
User pushed back on whether SigLIP was optimal. After analysis:

- **DINOv2** is self-supervised (no language), explicitly trained for **visual similarity and dense spatial correspondence**. It has no language alignment component.
- For pure image-to-image goal proximity matching with no text, DINOv2's representations are more appropriate. SigLIP's representations are shaped partly by language alignment, which is irrelevant — you never ask the critic about text.
- DINOv2 has richer spatial/geometric features and is state-of-the-art for tasks like dense correspondence, depth estimation, and semantic segmentation — all of which require understanding geometry, not language.
- DINOv2-B/16 is 86M parameters, fast at ~20ms per forward pass.

### Full list of alternatives considered
| Model | Params | Notes |
|---|---|---|
| **DINOv2-B/16** | 86M | **Recommended**. Best for pure visual similarity, no language alignment pulling features away from geometry |
| DINOv2-L/14 | 307M | Stronger but slower. Worth trying if B/16 underfits |
| SigLIP-B/16 | 400M | Good, but language-aligned — less appropriate for geometry-heavy tasks |
| SigLIP-SO400M | 400M | Stronger than B/16 but same argument applies |
| InternViT-300M | 300M | Vision encoder of InternVL-2. Best choice if you later upgrade to full VLM critic — same encoder, drop-in upgrade path |
| CLIP ViT-B/16 | 86M | Weaker than all above for image-image matching |

**Upgrade path**: if DINOv2-B/16 fine-tuning works, the next step is to swap in InternViT-300M (same ViT architecture but from InternVL-2), which gives you language conditioning and a clear upgrade path to a small VLM critic without redesigning anything.

## Intermediate Horizons: Lessons from Points2Plans

### The question
User raised: should intermediate imagined frames (steps 1 to H-1) also be evaluated by the critic, or just the final frame H?

### What Points2Plans does (the cleanest formulation in the literature)
Points2Plans (Huang et al., arXiv:2408.14769, Stanford) uses a relational dynamics model on 3D point clouds with the following separation:

**Eq. 3 — Goal achievement** (soft score, final state only):
```
argmax ∏_{g ∈ G̃} Dec^g_r(z_{H+1})
```
The probability of achieving goal predicates is only computed on the terminal latent state z_{H+1}. This is the planning objective.

**Eq. 4 — Feasibility constraints** (hard rejection, every intermediate step):
```
subject to Dec^c_r(z_t) < ε,  ∀c ∈ C,  ∀t ∈ {1, ..., H+1}
```
Infeasibility predicates (e.g., `Blocking(a,b)`, collision constraints) are checked at **every** timestep. If any intermediate state violates a feasibility predicate beyond threshold ε, the entire parameter sample is rejected and resampled. This is constraint enforcement, not progress estimation.

### Key insight from this design
The separation is:
- *"Did the plan achieve the goal?"* → **final state only, soft score**
- *"Is the plan physically executable at each step?"* → **every step, hard binary rejection**

These are two fundamentally different questions. Mixing them (soft progress at every step) is harder and less principled.

### Why the P2P approach doesn't directly transfer to Verify2Act
P2P's feasibility predicates (`Blocking`, `Above`, `Inside`) are grounded in **3D point cloud geometry** — their decoder literally predicts whether geometric relationships hold in 3D latent space. This works because the full geometric state is in the point cloud.

You have RGB images. The equivalent would require predicting "is the nut above the peg?" from 2D RGB, which runs directly into the same partial observability problem. Depth and occlusions destroy geometric signals in RGB.

### Recommended adaptation for Verify2Act
Adopt the P2P architectural separation with a **learned intermediate check** instead of rule-based filters:
- **Intermediate imagined frames (steps 1 to H-1)**: **Temporal consistency head (Head 2)** — learned contrastively from real trajectory frame pairs, measuring whether consecutive imagined frames form a physically plausible transition. This is richer than rule-based filters (bounding box, black frame) and catches diffusion drift/teleportation that rule-based approaches miss.
- **Final imagined frame (step H)**: **Goal proximity head (Head 1)** — `cosine_sim(head1(encode(Ĩ_H)), head1(encode(I_goal)))`.

Both heads share the same DINOv2-B/16 backbone — see Dual-Head Architecture section below.

**Honest limitation**: P2P's intermediate feasibility predicates check physical reachability grounded in 3D geometry. The temporal consistency head only checks whether the imagined rollout is visually coherent, not whether each intermediate state is physically reachable. This is a weaker claim than P2P and should be stated explicitly in the paper rather than claimed as parity with P2P's intermediate checking.

## Dual-Head DINOv2 Architecture (Finalized Design)

### Core architecture

```
DINOv2-B/16 backbone (shared, fine-tuned)
         |
    [CLS token, 768-dim]
         |
    ┌────┴────┐
    Head 1    Head 2
    Goal      Temporal
    Proximity Consistency
    (768→256  (768→256
    linear)   linear)
```

Both heads are lightweight linear projections on top of the shared DINOv2 CLS token. The projections map into a 256-dim embedding space where cosine similarity is computed. This is the standard SimCLR/MoCo pattern.

### How the two heads are used differently

**Head 1 (goal proximity)** — cross-image comparison, final frame only:
```
cosine_sim(head1(encode(Ĩ_H)), head1(encode(I_goal)))
```
Learns what visual features indicate task completion relative to a fixed reference.

**Head 2 (temporal consistency)** — within-rollout comparison, all consecutive pairs:
```
cosine_sim(head2(encode(Ĩ_t)), head2(encode(Ĩ_{t+1})))  for t = 1..H-1
```
Learns what physically plausible frame-to-frame transitions look like in the domain.

Same backbone, same forward pass per image. Both heads are matrix multiplications on top of cached embeddings — negligible compute beyond the backbone.

### Training objective

Joint InfoNCE with weighted sum:
```python
loss = λ₁ * InfoNCE_goal_proximity + λ₂ * InfoNCE_temporal_consistency
```
Start with **λ₁ = λ₂ = 1.0** (treat as hyperparameter). If temporal consistency loss dominates early training, reduce λ₂ — its signal (consecutive frame similarity) is weaker than goal proximity for a manipulation task.

**Goal proximity batch construction:**
- Positive: `(I_late_frame, I_goal)` from successful episodes (late = last 20% of timesteps)
- Negative: `(I_early_frame, I_goal)` from any trajectory (early = first 20%)
- Episode success flag required for positives — partially completed episodes never contribute positives regardless of timestep

**Temporal consistency batch construction:**
- Positive: `(I_t, I_{t+1})` — consecutive frames from real expert rollouts
- Negative 1: `(I_t, I_{t+k})` where k ≥ 3 — frames that skip steps (too abrupt; use k≥3 since adjacent frames in slow manipulation may look too similar)
- Negative 2: `(I_t, I_{t-1})` — temporally reversed transitions
- Negative 3: `(I_t from ep A, I_{t'} from ep B)` — cross-episode pairs

**Domain adaptation**: include a proportion of diffusion-generated image pairs in both batches to close the domain gap between training (real frames) and inference (diffusion outputs). Run a qualitative inspection of multi-step diffusion rollouts first to confirm diverse failure modes exist before committing to this.

### Training warnings
- Two InfoNCE losses pull the shared backbone in slightly different directions. Both push it toward manipulation-relevant visual features, so they are compatible but not identical.
- If one loss stagnates while the other improves, the backbone is being pulled toward one objective — adjust λ or extend backbone freeze epochs before unfreezing.
- The two objectives are complementary: goal proximity requires recognizing nuts-on-pegs state; temporal consistency requires detecting frame-to-frame physical discontinuities. Both benefit from the same domain representations.

## Inference Flow (Sequential Early-Abort)

The model is an encoder, not a classifier. Images are passed through the backbone one at a time (or batched); embeddings are cached; cosine similarities are computed outside the model.

```
Cache goal embedding (once per episode):
  e_goal = encode(I_goal)  → apply head1 → cache

Sequential rollout evaluation:
  Generate Ĩ_1 → e_1 = encode(Ĩ_1) → cache
  Generate Ĩ_2 → e_2 = encode(Ĩ_2) → cache
    → score = cosine_sim(head2(e_1), head2(e_2))
    → if score < threshold: ABORT → requery (diffusion failure)
  Generate Ĩ_3 → e_3 = encode(Ĩ_3) → cache
    → score = cosine_sim(head2(e_2), head2(e_3))
    → if score < threshold: ABORT → requery
  ...
  Generate Ĩ_H → e_H = encode(Ĩ_H) → cache
    → final consistency check passes
    → proximity = cosine_sim(head1(e_H), head1(e_goal))
    → CriticDecision: continue / reflect / requery
```

Early-abort saves diffusion compute on bad rollouts (diffusion forward passes are expensive relative to the critic). The backbone runs exactly once per frame regardless of how many heads are applied.

## Research Story (Final)

> "VLM self-reflection (ReflectVLM) is semantically strong but physically ungrounded and slow (~2–5s per query at 7B scale). Furthermore, VLM self-critique is epistemically entangled with its own proposal — a known failure mode of LLM self-correction (Huang et al., 2023). We show a lightweight 86M-parameter domain-adapted contrastive verifier — fine-tuned on demonstration temporal ordering rather than binary labels — provides faster (~20ms), more physically grounded, and independent verification. We identify two orthogonal failure modes of world-model-based planning — rollout integrity failure (diffusion incoherence) and goal proximity failure (coherent but wrong plan) — and show that evaluating them separately with a dual-head contrastive critic improves filtering over a single feasibility score. The temporal consistency head, trained contrastively on real trajectory frame pairs, provides the first learned intermediate evaluation mechanism for imagined rollouts from RGB without 3D geometric predicates."

## Honest Caveats (don't hide these)
- A 7B VLM will eventually outperform an 86M model as VLMs get better visual grounding. Acknowledge this.
- Contribution is narrow but real: speed, physical grounding, and the decoupled pipeline architecture.
- Verify2Act's main contribution is more likely the **pipeline architecture** (world model + separate verifier loop) than the specific critic. The critic is a replaceable module. Frame accordingly.

The `CriticDecision` 3-way logic in `verify2act/critic/inference.py`:
```python
# Extended logic with temporal consistency pre-filter:
# low consistency_score  → diffusion failure → requery (generate new rollout)
# high consistency + low proximity_score → reflect (rollout coherent but plan wrong)
# high consistency + high proximity_score → continue (plan is good, execute)
```
This three-way distinction is more informative than the original design because it separates **world model failures** (incoherent rollout) from **planning failures** (coherent rollout, wrong goal). The old single feasibility score collapsed both failure modes. The `consistency_score` is the mean of per-step Head 2 cosine similarities; the `proximity_score` is the final-frame Head 1 cosine similarity against `I_goal`.

The world model in `pipeline/world_model.py` has two modes:
- `OracleWorldModel` — restores sim state directly (used for debugging/ablations)
- `DiffusionWorldModel` — generates predicted images via diffusion (used in real pipeline)

The diffusion WM outputs **images**, not latent vectors. This confirms the critic must be image-in, score-out.

## Immediate Next Steps

### Step 0 (30 min): State oracle diagnostic
Train a simple MLP on raw qpos/qvel from `.npz` files → binary `label_reachable`. If AUROC >> 0.5, labels are meaningful but not visually observable. If even this fails, `compute_labels.py` itself is broken (horizon too short, expert policy quality issues). **The contrastive design still uses the episode success flag to determine positive pairs — if the flag is unreliable, both approaches fail.**

### Step 0.5 (qualitative, 20 min): Inspect multi-step diffusion rollouts
Check whether the diffusion world model produces diverse failure modes (drift, teleportation, texture collapse) across H steps. If the model is very good and rarely produces incoherent sequences, the temporal consistency filter won't fire often enough to show a measurable effect in ablation. Confirm the failure modes exist before building around them.

### Step 2: Implement `ContrastivePairDataset`
Two sampling modes in the same dataset class:
- Goal proximity mode: (late + success flag, goal) positive / (early, goal) negative
- Temporal consistency mode: (I_t, I_{t+1}) positive / (I_t, I_{t+k≥3}) shuffled / cross-episode negative

### Step 3: Implement `DINOv2DualHeadCritic` with joint InfoNCE loss
Shared DINOv2-B/16 backbone + two 768→256 linear projection heads. Joint InfoNCE with λ₁=λ₂=1.0 as initial hyperparameter. Include a proportion of diffusion-generated frames in training batches for domain adaptation.

### Step 4: Fine-tune and evaluate
Ablations to run:
- Head 1 only (goal proximity) vs Head 1 + Head 2 (dual) — does temporal consistency help?
- Without diffusion-generated frames vs with — does domain adaptation matter?
- w/ vs w/o early-abort — does consistency pre-filtering improve downstream task success rate?
