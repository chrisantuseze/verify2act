# Points2Plans Integration: Corrected Understanding

## Addressing Critical Misconceptions

Based on reviewing the Points2Plans codebase and paper, here are corrections to the integration plan:

---

## 1. Predicate Generation: Decoder's Role ✓

**YOUR QUESTION**: "Why do we generate the predicates outside of the Points2Plans framework? Is that not handled by the decoder?"

**CORRECTED UNDERSTANDING**:

You're absolutely right! The **decoder generates predicates during inference**, not us manually computing them.

### How it Actually Works:

```python
# During inference, the decoder outputs:
outs_decoder = self.classif_model_decoder(node_latent, edge_index)

# Decoder outputs include:
{
    'pred_sigmoid': relational_predicates,      # [batch, num_edges, num_predicates]
    'predicted_pose': object_poses,              # [batch, num_objects, pose_dim]
    'env_identity': environment_features,        # [batch, num_objects, 3]
    'grasp_identity': graspability/feasibility   # [batch, num_objects, 1]
}
```

### Correct Data Flow:

**Training** (what you did):
```
Simulation → Point clouds + Manually computed predicates → Train decoder to predict them
```

**Inference** (what we need):
```
Robosuite obs → Point clouds → Encode → Decoder predicts predicates (NOT manual computation)
```

### What We Actually Need to Provide:

| Component | Training | Inference |
|-----------|----------|-----------|
| Point clouds | ✓ (from simulation) | ✓ (from robosuite) |
| Object poses | ✓ (for supervision) | ✓ (for reference) |
| **Predicates** | ✓ (ground truth labels) | ✗ (decoder predicts!) |
| Feasibility | ✓ (ground truth labels) | ✗ (decoder predicts!) |

**Key Insight**: The `StateConverter` should NOT compute predicates manually. It only needs to:
1. Generate point clouds
2. Extract object poses (for reference, not supervision)
3. Build one-hot encodings
4. Let the decoder predict everything else

## 2. Execution Strategy: Closed-Loop with Replanning ✓

**YOUR QUESTION**: "When a plan/goal is generated by the LLM, does it get executed open loop with no feedback and replanning or is it closed loop?"

**CORRECTED UNDERSTANDING**:

Points2Plans uses **closed-loop execution with replanning at each primitive**.

### Two-Level Control Architecture:

```
Level 1: LLM (High-Level Task Decomposition)
├─ Input: "Put all objects in bin"
├─ Output: Goal predicates [On(milk, bin), On(cereal, bin), ...]
└─ Frequency: Once per task (or when task changes)

Level 2: Dynamics Model (Low-Level Action Planning)
├─ Input: Current state + Goal predicates
├─ Output: Next primitive action (pick object X, place at Y)
├─ Feasibility: Checks grasp_identity and collision
└─ Frequency: Every primitive (closed-loop replanning)

Level 3: Robot Controller (Motion Execution)
├─ Input: Primitive action parameters
├─ Output: Joint trajectories
└─ Frequency: Every control timestep
```

### Execution Flow:

```python
# LLM generates goals ONCE
goals = llm.generate_goals("Put all objects in bin", objects, initial_state)
goal_predicates = convert_to_tensor(goals)

# Closed-loop execution with replanning
while not goal_achieved:
    # 1. Get current state from robosuite
    current_state = state_converter.convert(obs)
    
    # 2. Dynamics model plans NEXT PRIMITIVE (closed-loop)
    action = planner.plan_action(current_state, goal_predicates)
    
    # 3. Execute ONE primitive (pick OR place)
    success = executor.execute_primitive(action)  # This is a trajectory
    
    # 4. Check if primitive succeeded
    if not success:
        # Replan with updated state
        continue
    
    # 5. Update observation for next iteration
    obs = env.get_observation()
    
    # 6. Check goal satisfaction
    current_predicates = decoder.predict_predicates(current_state)
    if matches(current_predicates, goal_predicates):
        break
```

### Key Points:
- **LLM**: Called once (or when subtask completes)
- **Dynamics model**: Called at every primitive boundary (closed-loop)
- **Robot controller**: Executes trajectories between primitives
- **Replanning**: Happens if primitive fails OR after every primitive completion

## 3. Cost Function: Feasibility Check ✓

**YOUR QUESTION**: "Whats the idea of a cost? Is this the predicate feasibility check in the paper?"

**CORRECTED UNDERSTANDING**:

The "cost" is actually a **feasibility check**, not an optimization objective!

### From the Code (`base_RD.py` line 680-740):

```python
for each_sample_id in range(action_selections):
    feasibility_leap = 1  # Assume feasible
    
    for seq in range(len(task_planner)):
        # Check grasp feasibility
        for each_min_identity in range(...):
            if self.min_identity[each_min_identity][1] > 0.5:  # Unfeasible!
                feasibility_leap = 0
        
        # Check collision feasibility
        if collision_detected:
            feasibility_leap = 0
    
    # Only use this action if feasible
    if feasibility_leap == 1:
        return action
```

### Feasibility Checks:

1. **Grasp Feasibility** (`grasp_identity` from decoder):
   - Decoder predicts: Can object X be grasped in this state?
   - Binary: 0 = graspable, 1 = not graspable
   - Check: `if grasp_identity[obj_id] > 0.5: infeasible`

2. **Collision Feasibility** (geometric check):
   - After predicting next state, check if objects collide
   - Uses bounding boxes and 2D collision detection
   - Check: `if objects_overlap: infeasible`

3. **Goal Satisfaction** (relational predicates):
   - Compare predicted predicates with goal predicates
   - Not a binary check, but used to evaluate progress
   - Check: `if predicted_predicates ≈ goal_predicates: done`

### What "Cost" Really Means:

The paper uses "cost" informally to mean:
- **Binary feasibility**: Action is either feasible (cost=0) or infeasible (cost=∞)
- **Not continuous optimization**: Not minimizing a differentiable cost function
- **Sampling-based**: Sample N actions, filter infeasible ones, pick first feasible

**Corrected**: It's a **feasibility-based rejection sampling**, not cost minimization!

## 4. Step Definition: Key Action Steps (State Transitions) ✓

**YOUR QUESTION**: "In run_episode, what does the step entail? Trajectories or key action steps?"

**CORRECTED UNDERSTANDING**:

A "step" in Points2Plans is a **key state transition** (discrete primitive), NOT a trajectory timestep.

### Points2Plans Action Representation:

From your training data:
```
Episode structure:
├─ State 0: Initial state
├─ State 1: After pick (gripper closed, object lifted)
├─ State 2: After place (gripper open, object released)
├─ State 3: After pick (next object)
└─ ...
```

Each transition = one primitive action (pick OR place)

### Mapping to Robosuite:

```python
# Points2Plans step (discrete primitive)
points2plans_action = {
    'skill': 0,        # pick-place
    'object_id': 2,    # milk
    'target_id': 4,    # bin
    'offset': [0.01, -0.02]
}

# Robosuite execution (continuous trajectory)
def execute_primitive(action):
    """
    Execute ONE Points2Plans primitive as a multi-phase robosuite trajectory.
    """
    # Phase 1: Move to object (multiple robosuite steps)
    for t in range(100):
        ee_action = compute_control(ee_pos, target_pos)
        obs, _, _, _ = env.step(ee_action)
    
    # Phase 2: Grasp (multiple robosuite steps)
    for t in range(50):
        gripper_action = [0, 0, 0, 1.0]  # Close gripper
        obs, _, _, _ = env.step(gripper_action)
    
    # Phase 3: Lift
    for t in range(100):
        ...
    
    # Phase 4: Move to target
    for t in range(150):
        ...
    
    # Phase 5: Release
    for t in range(50):
        ...
    
    # Return final state after primitive completes
    return obs
```

### Correct Control Loop:

```python
def run_episode(self, goal_description, max_primitives=20):
    """
    Args:
        max_primitives: Maximum number of discrete primitives (NOT trajectory steps)
    """
    obs = self.env.reset()
    
    # LLM: Generate goals once
    goals = self.llm_planner.generate_goals(goal_description, ...)
    goal_predicates = self.llm_planner.goals_to_predicates(goals)
    
    # Closed-loop primitive execution
    for primitive_idx in range(max_primitives):
        # Current state
        state = self.state_converter.convert(obs)
        
        # Plan next primitive (Points2Plans step)
        action = self.planner.plan_action(state, goal_predicates)
        
        # Execute primitive as trajectory (many robosuite steps)
        obs = self.executor.execute_primitive(action)  # This is 200-500 robosuite steps!
        
        # Check goal
        current_predicates = self.planner.get_current_predicates(state)
        if goal_satisfied(current_predicates, goal_predicates):
            return True
    
    return False
```

**Key Insight**: 
- `max_steps` in planning = max primitives (pick, place, push)
- Each primitive = 200-500 robosuite timesteps
- Planning happens between primitives (closed-loop)

## 5. Tree Search: When All Samples Fail ✓

**YOUR QUESTION**: "Isn't tree search done when all plans fail the feasibility check?"

**CORRECTED UNDERSTANDING**:

Yes! Tree search is a **fallback when sampling fails**.

### From the Code (`base_RD.py` line 760):

```python
for planning_iter in range(10):  # Max 10 sampling iterations
    # Sample N candidate actions
    for each_sample_id in range(action_selections):
        if feasibility_check_passed:
            return action  # Found feasible action!
    
    # If we reach here, NO feasible action found
    print('No feasible solution found this iteration. Continue sampling.')
    # Continue to next iteration with new samples
```

### Sampling Strategy:

**Base case** (what happens most of the time):
1. Sample N actions (e.g., 50 candidates)
2. Check feasibility for each
3. Return first feasible one
4. **Success rate**: High (usually finds feasible action in 1-2 iterations)

**Tree search** (when sampling fails repeatedly):
1. After K failed iterations (e.g., K=5)
2. Build explicit search tree over action sequences
3. Explore multi-step ahead (depth > 1)
4. Find feasible trajectory through tree search

### When Tree Search is Needed:

| Scenario | Sampling Works? | Need Tree Search? |
|----------|----------------|-------------------|
| Simple pick-place | ✓ | No |
| Object blocking goal | ✓ (usually) | Maybe |
| Complex dependencies | ✗ | Yes |
| Narrow feasible region | ✗ | Yes |

### Implementation Note:

The paper mentions tree search, but the **base implementation uses rejection sampling**. Tree search is:
- An **advanced feature** for complex scenarios
- Not always necessary for standard tasks
- Can be added later if sampling fails too often

**Recommendation**: Start with rejection sampling (already in code), add tree search only if needed.

## What This Means for Implementation

### 1. StateConverter is Simpler
- **Remove**: Manual predicate computation
- **Keep**: Point clouds, poses, one-hot encodings
- **Trust**: Decoder to predict predicates

### 2. Planning is Closed-Loop
- Plan at primitive boundaries, not trajectory level
- Replan after every primitive execution
- Handle failures naturally (just replan)

### 3. Feasibility, Not Cost
- Binary checks (feasible/infeasible)
- Rejection sampling, not optimization
- First feasible action wins

### 4. Primitives, Not Steps
- One primitive = many robosuite steps
- max_steps = max primitives (e.g., 20)
- Expect 10-50 primitives per episode

### 5. Tree Search is Optional
- Start with sampling (already implemented)
- Add tree search only if needed
- Most tasks work fine with sampling

This corrected understanding should lead to a much simpler and more accurate implementation!
